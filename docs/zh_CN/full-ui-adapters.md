# 完整 UI 插件适配器 — 研究与路线图

**论点：复杂插件的完整 UI 支持是一架梯子，而不是一道悬崖。** 担忧
认为「完整插件编辑是一个庞大工程」的前提，是把工作单元定义为
屏幕：永远手动重建每个插件的每个管理页面，并且始终落后。研究
表明工作单元是*架构系统*。成熟的插件已经停止手写
多年前就有了自己的设置页面；它们将字段声明为数据并进行渲染
以通用方式。如果 Minimal 能够导入这些声明，一个适配器映射器就能覆盖整个
插件系列，界面就会自然生成。

研究依据（2026-07-06）：对 Gravity Forms 2.10.5 和 Gravity 的源代码级审计
SMTP 2.2.0（生态系统中两个最复杂的插件，经过刻意选择以
针对当前 Minimal 扩展机制的清单，涵盖最棘手的情况）。接线
从一开始就排除了将其现有管理 UI 移植到 Minimal；问题在于
适配器方案是否能扩展到完整覆盖。

## 主要发现

1. **两个插件在关键部分都由架构驱动。** Gravity Forms 使用一个共享的
   设置引擎（`includes/settings/class-settings.php`，23 种字段类型），用于其
   插件设置、表单设置、通知、确认，以及每个附加组件的
   设置和信息源。Gravity SMTP 将全部 21 个连接器的配置字段声明为数据
   （`settings_fields()` 描述符数组，约 8 种组件类型）。两者都不会手写
   设置 HTML。能够渲染其架构的外部 UI 几乎可以渲染其全部
   其管理界面，包括尚不存在的附加组件中的页面。

2. **写入路径很清晰。** GF 的整个表单定义（字段、设置、
   通知、确认）通过一个 JSON 文档往返传输
   `PUT /gf/v2/forms/{id}`；条目、备注和 feed 均支持完整的 REST CRUD。Gravity SMTP
   将所有内容存储在两种 JSON 选项结构和四张自定义表中，并带有使用随机数保护的
   每次变更都使用 admin-ajax 端点。没有抓取屏幕，也没有向管理页面 POST 的变通方案。

3. **Minimal 已经拥有大部分客户端机制。** 三个由架构驱动的表单
   目前存在的系统（编辑器面板、界面创建/编辑、区块检查器表单）
   包含三套不一致的字段词汇，以及 `sectionsRoute` 显示模型
   该模式已经将详情渲染移至服务器端。最高杠杆率的单一
   此移动是整合，而非发明。

4. **真正需要定制的表面很少，而且可以跳过。** 在 GF 中，它是拖放
   表单编辑器（以及小型条件逻辑规则构建器）。在 Gravity SMTP 中，它是
   仅处理 Google/Microsoft/Zoho 的 OAuth 握手。两者中的其他所有内容
   插件的是列表、详情视图和由架构声明的表单。定制层已经
   已经有经过验证的答案：委托，正如页面构建器所做的那样（「在 Gravity Forms 中编辑」
   只需点击一次，构建器风格的界面无需 wp-admin 外壳）。

## 架构框架：四个阶梯

该提案是一条升级阶梯。每个阶梯都可以独立交付，并且每个阶梯都会
下一个更便宜，而插件的适配器可以在任意层级停止，并使用 wp-admin
深层链接涵盖其余内容。始终遵循逐字原则：Minimal 根据 schema 渲染
在运行时从正在运行的插件中读取，因此当插件添加字段或附加组件时，
覆盖范围会自动更新。手工构建的界面会过时；导入的 schema 不会。

### 第 1 层 — 一个表单引擎（核心）

将三个字段词汇合并为单一的架构驱动表单渲染器，定义于
由 Minimal 提供，而非由任何单个插件提供）：字段类型包括 text、textarea、number、select，
带自定义选项的选择框、单选框、复选框、切换开关、隐藏字段，以及每个字段的 `required`，
`default`、`choices`、`help`、`placeholder`、验证消息，以及简单的
`dependency` 规则（当字段 A 等于 X 时显示字段 B；GF 会评估这些
目前通过一小组操作符在客户端实现，Minimal 的 `when` 条件已经
同一理念）。编辑器面板引擎（`panelInput`/`panelCard`）是正在使用的
种子：它已经处理选择项、切换开关、脏状态跟踪和锁定字段
升级。将其与保存后 payload 解耦，使任何调用方都能将其指向一个
`{ schemaRoute, valuesRoute, writeRoute }` 三元组。

下游所有功能都复用这一点：表面创建/编辑会为
免费，编辑器面板不会损失任何功能，设置界面也因此成为可能。

### 第 2 层 — 设置表面 + 架构映射器（乘数）

新的表面形态：

```php
'settings' => [
  'schemaRoute' => 'minimal-admin/v1/gf/settings-schema/{tab}',
  'valuesRoute' => 'minimal-admin/v1/gf/settings/{tab}',
  'writeRoute'  => 'minimal-admin/v1/gf/settings/{tab}',
  'tabs'        => [ ... ],
],
```

客户端渲染表单引擎组的标签页，并将更改后的值通过 PUT 写回。所有
智能存在于适配器 shim 中，它承担两项工作：

- **架构映射。** 将插件的原生字段描述符转换为 Minimal 的表单
  词汇表。这是每个*框架*编写一次，而不是每个屏幕编写一次。GF Settings
  映射器（23 种类型，其中大多数与 Minimal 一一对应）涵盖 GF 插件设置、表单
  设置、通知、确认，以及每个 GFAddOn 的插件/表单/信息源
  设置，无论现在还是未来。Gravity SMTP 映射器（约 8 种组件类型）涵盖所有
  21 个连接器，以及常规/日志/警报选项卡。无法映射的字段类型（GF 的
  `generic_map`、`notification_routing`；任何包含无法解析的可调用对象的内容）都会
  计数并显示为「N 个高级字段——在 wp-admin 中编辑 ↗」，正是
  ACF 面板已经交付的锁定字段模式。
- **值处理。** 在插件自身的 PHP API 中读写，位于
  垫片，遵循插件自身的能力模型。对于 GF：`GFAPI`，
  `update_plugin_settings()`，用于通知/确认编辑的完整表单 PUT，
  始终通过 `GFCommon::current_user_can_any()` 进行门控。对于 Gravity SMTP：
  服务容器的数据存储（保留 `GRAVITYSMTP_*` 常量锁定
  行为），并由细粒度的 `gravitysmtp_*` 权限进行门控。Shim 规则仍然有效：
  按前缀限定的查询，绝不读取 `unserialize()` 第三方数据块、敏感字段
  哨兵值（Gravity SMTP 将机密值掩码为 `****************`；未更改的哨兵值
  必须跳过写入，以匹配其自身的保存语义）。

这一阶梯意味着「完整 UI 支持」不再只是设想：它将两者都转换为
插件的设置体系，而这按屏幕数量计算占据了其管理界面的大部分。

### 第 3 层 — 更丰富的表面原语

沿着研究表明实际需要的方向扩展现有词汇，在
大致优先级顺序：

- ~~**参数化操作。**~~ ✅ 已交付（v0.13.0）：操作上的 `fields` 和
  正文中的 `{item.key}` 替换。已交付 Gravity SMTP「发送测试」，
  FluentSMTP 「重新发送至…」（v0.24.0 周期）、GF 条目重新发送。
- ~~**批量选择。**~~ ✅ 已交付（v0.13.0）：复选框列加批量操作
  复用相同操作描述符的条形图（集合上的 `bulk`）。GF 条目批量
  收藏/标记为已读/标记为垃圾邮件/移至回收站，以及邮件日志清理都通过它实现。
- **编辑器状态面板。** ✅ 已发布（v0.25.0 周期，2026-08-08）：状态卡
  形态移植到编辑器侧栏，作为 `statusRoute` 面板类型，位于
  `minimal_admin_editor_panels`——入口显示服务器摘要和语气，模态框显示统计
  行和声明式操作（通过主题化确认框进行确认/危险操作），

  往返。第一个使用者是 CaptainCore Manager 的新闻通讯面板，它
  完全从其自身仓库注册（这是「自行提供适配器」的证明，适用于
  按文章范围限定的动词：send-newsletter、purge-this-page、share-to-social 都适用）。
- **表面统计卡和图表行类型。** `status` 卡片（已发布
  2026-07-10）涵盖列表上方的统计行和操作；图表行已发布
  v0.13.0（见上文）。仍缺少：按项目显示的统计卡片，以及 GF

- ~~**更丰富的 `sectionsRoute` 行类型。**~~ ✅ 已交付（v0.18.0 开放，2026-07-17）；
  请参阅上面的第 3 层条目。
- ~~**列表中的行操作**~~ ✅ 已交付（v0.13.0），内容列表 `⋯` 行
  菜单模式已泛化。第三级导航仍在等待真正的适配器
  要求它；到目前为止，选项卡加上 main/manage/views 已覆盖所有内容。

### 第 4 层 — 定制层（做出决定，不要无意中进入）

对于超出 schema 范围的界面，有两种候选策略，推荐的是
首先：

- **委托（推荐，也是已发布的模式）。** GF 表单编辑器是
  之于 Gravity Forms，正如 Elementor 的画布之于 Elementor，而 Minimal 已经决定
  在这种情况下：检测、深层链接，绝不重建。研究进一步证实：
  编辑器约有 100 个设置面板是手工编写的内联 JS，拖放层是一个
  完整应用，而 GF 自己的编辑锁定受限于管理屏幕（外部编辑器
  会绕过它）。与此同时，收益很有限，因为表单*管理*（列表、
  条目、设置、通知）是日常工作；表单*构建*则是偶发工作。
- **插件提供的 JS 视图（已拒绝）。** 允许适配器注册任意 JS
  视图将成为无需构建、单文件、可 grep 架构的终点，以及一个
  安全回归（Minimal 文档中包含任意第三方代码，而该文档
  目前只有刻意设置为页面级别的 `minimal_admin_template_footer` 入口
  允许这样做，用于开发者工具）。如果某个界面无法用描述符表达，
  答案是深层链接。

一条长期备注，已记录以确保该选项保持可见：GF 的表单编辑器写入一个
通过 `PUT /forms/{id}` 生成干净、完全可枚举的 JSON 文档（`display_meta`），
字段面板是程序化的（`GF_Fields::get_all()`），每种类型的设置键是
可枚举，条件逻辑只是简单的规则 JSON。由 Minimal 构建的表单编辑器是
因此无需接触 GF 的 JS *即可实现*。这将是产品层面的决定，涉及
其规模相当于「Minimal 再构建一个编辑器」，这不是适配器功能，而第几层都没有
1-3 会阻止它。该选项（「80% 编辑器」），加上开发者表面
兄弟项，其边界已在 `docs/native-editors.md` 中明确划定。
在同类项目中，只读数据库查看器已在 v0.22.0 周期发布；
文件浏览暂时搁置，80% 的编辑器仍是一个有意为之的下注，而不是
尚未完成。

## 案例研究：Gravity Forms 覆盖图

适配器：`includes/adapters/gravity-forms.php`。日常表单工作位于 Minimal 中；
表单*构建*仍然是深层链接（第 4 阶梯）。

| 表面 | 状态 | 机制 |
|---|---|---|

## 风险与未决问题

- **架构可调用项。** GF 描述符可能携带 PHP 可调用项（选项、渲染
  回调）。映射器会解析能够解析的内容，其余内容计为锁定字段；
  绝不尝试序列化可调用对象。
- **完整表单 PUT 并发控制。** 编辑一条通知会对整个表单执行往返
  JSON，因此两个编辑器可能互相覆盖。通过在内部执行读-改-写来缓解
  垫片（一次请求、最小窗口），并在此之前检查 `date_updated`
  写入；GF 自身的锁定仅限于管理界面，无法在这里提供帮助。
- **版本漂移。** 运行时架构导入会自动修复字段，但映射器代码
  涉及插件内部实现（GF 的 Settings 类、Gravity SMTP 的容器名称）。
  每个 shim 都已经检查插件是否存在；映射器还必须检查类/
  检查方法是否存在，并降级为深层链接，绝不导致致命错误。
- **加密数据块。** GF 插件扩展设置选项在静态存储时已加密；始终通过
  通过 `get_plugin_settings()`/`update_plugin_settings()`，绝不使用原始选项。
- **范围纪律。** 这份路线图的失败模式是重新构建 wp-admin 的一个
  一次一个描述符。`stats`/chart/bulk 新增功能受两个
  案例研究插件实际需要的功能；任何只有一个假设插件会使用的功能
  等待该插件存在。

## 我们永远不会构建的内容

嵌入插件管理页面（iframe 或其他方式）、插件注册的 JS 视图，以及
通用的类 XML 布局语言、拖放编辑器重建，以及逐屏手工构建的
克隆插件 UI。指向 wp-admin 的深层链接并非道歉；它是逃生
让每个阶梯都保持诚实的入口。
