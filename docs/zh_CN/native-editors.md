# 原生编辑器和开发者界面——适配器阶梯之上的台阶

**状态：一个已交付，两个搁置（已于 2026-08-06 在 v0.24.0 中更新
树）。**只读
数据库查看器（案例 2）已在 v0.22.0 周期发布，完全按照以下方式构建
此处划定的范围；Gravity Forms 的 80% 编辑器和文件浏览器仍然
搁置且未排期。最初的前提仍然成立：本文档存在的目的就是
当其中一项拉力足够大、值得构建时，范围论证已经
已完成，边界也已经划定。查看器证明了该模式
它扩展了 `full-ui-adapters.md`，
其四级阶梯以「委托定制界面」告终；这就是该映射
哪些功能可以构建在其之上，以及判断某项功能是否
适合它的地方出现。

## 决策测试

适配器阶梯的第 4 阶段指出：当插件界面无法用
描述符，并深度链接到它。该规则混淆了两种不同情况，而
将它们分开正是整个洞见所在：

1. **屏幕就是画布。** 交互本身就是产品：拖动
   Elementor 分区、绘制 Bricks 布局、GF 的实时表单预览。
   这些工具生成的产物要么不透明（构建器元数据 Blob），要么无法分离
   从渲染循环中移除。委托在这里永远是正确的。这绝不会
   更改。
2. **屏幕是覆盖在整洁文档上的精致表单。** UI 看起来
   复杂的东西，但它*产生*的是可枚举、可往返的数据
   带有公开写入路径的文档。在这里，Minimal 不需要该插件的
   界面：它可以在 Minimal 中为该文档构建自己的编辑器，
   理念，而插件无法辨别其中的差异。

因此测试是：**忽略 UI，查看产物。** 它是否是一个整洁的文档
（通过 REST 路由的 JSON、可枚举架构、版本化选项结构）？
然后，原生编辑器*成为可能*，问题就变成了产品范围。是否
它不透明，还是交互本身就是产品？那么答案就是深度链接
永远如此，无论需求有多大，都不应重新开放它。

目前有两个系列通过了测试，而且它们差异足够大，应分别对待
分别处理：**干净文档上的原生编辑器**（Gravity Forms 案例）
以及**面向开发者的界面，而不是站点基础组件**（数据库查看器、文件
浏览器），其中「文档」本身就是站点。

## 案例研究 1：Gravity Forms 表单编辑器（80% 编辑器）

### 为什么它通过了测试

根据 2026-07-06 的源资料研究（详情见 `full-ui-adapters.md`）：

- GF 表单是一个 JSON 文档（`display_meta`），可通过
  `PUT gf/v2/forms/{id}`。字段、设置、通知和确认
  全部都包含在其中。
- 字段面板以编程方式生成：`GF_Fields::get_all()` 枚举每一个
  已注册的字段类型，包括附加组件提供的字段类型。
- 每种类型的设置键都可枚举，条件逻辑也是一个小型规则
  JSON（`{ actionType, logicType, rules: [{ fieldId, operator, value }] }`），
  这正是 Minimal 自己的 `when`-条件结构的成熟版本。
- GF 自身的编辑器是在此文档之上手工编写的内联 JS。没有任何
  它所执行的是特权操作；外部编辑器写入同一文档会产生
  GF 渲染和编辑的表单可以互换。

### 范围决策：80%，而不是对等

一个对等编辑器（GF 的拖放画布、约 100 个手工编写的设置面板，
实时预览）未通过画布测试，并会让 Minimal 永久陷入功能对等
跑步机。Stackable 的教训同样适用：追逐插件自己的 React UI 是一条
Minimal 因胜出而输掉的竞赛。

80% 编辑器是另一种产品：**带字段编辑的表单管理**，
遵循 Minimal 的列表优先理念，涵盖人们实际对表单进行的编辑
那些已经存在的功能：

- **字段列表**——添加、删除、重新排序（菜单拖拽模式）、复制。
  渲染为行，而不是画布；静态预览面板可以渲染表单
  通过 GF 自己的前端标记在岛式预览中呈现，只读。
- 通过共享表单引擎实现的**字段级基础功能**：标签、描述，
  必填、占位符、选项（添加/重新排序/默认值）、字段大小、管理
  标签。设置可映射到表单词汇的字段类型将获得完整
  编辑；其余部分呈现各自映射的子集，并显示带锁定的计数
  「在 Gravity Forms 中编辑 ↗」（ACF 锁定字段模式）。
- **表单设置、通知、确认**——Phase-2 GF Settings
  映射器 ✅ 已交付（v0.13.0 周期，2026-07-12）：通过
  按项目限定的设置视图，通知作为列表视图，并带有每日字段
  编辑；确认编辑被有意跳过（表单构建时
  工作，而不是每天运行）。80% 编辑器会与它们组合，而不是
  包含这些内容。
- **条件逻辑，读取优先**：将现有规则呈现为句子
  （「当 Budget 大于 500 时显示」）。编辑规则是 v2 决策；
  规则 JSON 很简单，但要做好规则构建的 UX 并不简单。

明确排除，永久排除：拖放画布、实时样式预览、布局
列、定价/产品字段连接，以及超出该范围的附加组件订阅源界面
设置映射器所覆盖的范围。深层链接只需点击一次，GF 的编辑器也很不错。

### 承重风险

- **完整表单 PUT 并发控制。** 一次通知编辑会往返传输整个
  表单 JSON；两个编辑器可能互相覆盖，而 GF 自己的锁定机制
  受限于管理界面，因此无法提供帮助。缓解措施：在内部执行读-改-写
  写入前先通过 `date_updated` 检查的垫片，加上 Minimal 侧的锁定
  如果这一功能最终发布（`_edit_lock` 模式已证明 core 和 Minimal 可以共享
  一种锁定协议；GF 需要通过表单元数据实现相同的理念）。
- **版本漂移。** 映射器在运行时读取架构，因此*字段*会自我修复，
  但编辑器对 `display_meta` 结构的假设属于代码。通过保护
  每次读取都进行处理，降级为深度链接，永不致命（既定的 shim 规则）。
- **必须写清楚自动化边界。** 一旦请求需要
  如果需要超出表单词汇的、针对每种字段类型定制的 UI，答案就是
  已锁定的数量，而不是新的控件。这正是使
  让区块检查器保持诚实。

### 成本，实话实说

这已经是「Minimal 构建第二个编辑器」的规模：可以想象区块检查器的工作量，
不是适配器。字段列表 + 基础功能 + 测试套件，估算一个完整周期。
前置基础设施（条目范围设置、Settings-framework 映射器、
通知写入路径）已在 v0.13.0 周期交付，管理
围绕搁置编辑器的循环仍在不断扩大：条目工作流
（star、spam、bulk、resend）在 v0.12.0 中，以及 v0.18.0 中的 Feeds 视图，该视图
通过 GF 自己的模型列出每个附加组件订阅源，并支持开关和删除
同时配置仍通过深层链接访问，因此「不提供附加组件 feed UI」
即使订阅源变得可见，这条边界仍然保持不变。截至 v0.24.0，没有字段编辑
代码已存在于树中（`includes/adapters/gravity-forms.php` 仅写入
表单设置和通知通过 `GFAPI::update_form`）；其中
在做出承诺之前仍需完成的事项没有变化：对该表单管理
在实际启用 Gravity Forms 的站点上进行深度验证，因此这个判断是有依据的，
并非假定如此。

### 通用化

GF 是参考对象，而不是目标。相同的 80% 编辑器形态适用于任何插件
其产物是干净文档：Fluent Forms（表单以 JSON 存储在其自身的
带 REST 的表格）、Redirection 分组、WP Mail SMTP 连接向导。
规则：针对最复杂且结构良好的案例，只构建一次文档编辑器
（GF），提取可泛化的内容到表单引擎中，并让其他适配器
与映射器一起选择启用，正如设置界面乘数一样。

## 案例研究 2：数据库查看器（开发者界面）

**✅ 已交付（v0.22.0 周期，2026-07-24）** — `/minimal-admin/database`，构建用于
以下范围：`includes/class-minimal-admin-db.php`（三个 GET 路由位于
`manage_options`，针对 information_schema 的标识符白名单，LIMIT
遵循 10k 分页窗口和封顶的筛选计数，以及按单元格
字节上限，并为行详情重新获取预留更大空间），再加上定制客户端视图
（表格列表 → 分页行 → 行详情模态框）。套件：`tests/database.test.js`。
边界保持不变：不写入、不提供 SQL 控制台，序列化 blob 原样渲染。

**同一周期内扩展（2026-07-24）**，新增的两项内容仍然
在原有范围内，先明确评估引入它的利弊
进一步扩展（关于 phpMyAdmin 的问题，答案是否定的）：

- **结构选项卡**（`GET /db/structure`）——列以及来自 `indexes_of()` 的
  `SHOW INDEX`。仅元数据，因此无论表大小如何都免费，这是
  为什么此选项卡不受限制，而 Rows 仍采用窗口化显示。
- **健康视图**（`GET /db/health`）——固定的检查注册表（孤立扫描、
  索引和引擎维护、碎片整理、自增空间、修订
  以及队列积压），缓存 10 分钟，并汇总为一项系统健康
  行。套件：`tests/db-health.test.js`。

三个属性使这些新增功能无需额外成本，而不是新的界面，并且任何
未来的检查必须同时满足以下三点：**SQL 由用户编写**（没有请求
参数可以到达它，因此不会在
查看器已经具备的功能）；**扫描范围有限**，受相同的 `COUNT_CAP`
子查询惯用法作为 `rows()`，并在 `SCAN_MAX_ROWS` 之上完全跳过，因此
诊断工具不会伤害最需要它的大型站点；并且**唯一的
解决方案是提供一个 WP-CLI 命令来复制**。最后这一项是承重结构。
「清理」按钮正是将此查看器变成编辑器的那一步，
以下的推理也没有改变。复制命令会将答案交给
将写入操作交给管理员自己的 shell，在它应在的位置执行，同时保持 Minimal 的主张
这在字面意义上是正确的。

范围界定时出现并被否决的刻意非目标：一个
**数据库转储**。只读并不意味着无害，尤其是在读取是完整读取时。一个
转储会将任何身份验证漏洞的影响范围从「管理员读取封顶的
每次显示一页行」变成「一次请求返回每个密码哈希、客户
地址、存储的 SMTP 密码和许可证密钥」，以及反复出现的现实问题
此领域中的 CVE 是某个导出插件将 `.sql` 留在了 Web 可访问的
目录。Minimal 已经有备份工具系列（UpdraftPlus、Duplicator，
Disembark、WPvivid），由其负责该威胁模型及恢复方案；这
界面，或者 WP-CLI，才是诚实的答案。如果将来重新考虑，唯一
合理的形态是流式传输（永不写入磁盘），通过 POST 创建，并且
由一次性短 TTL 令牌使用，默认仅返回结构，并且
除非明确选择加入，否则会对包含凭据的列进行脱敏，并记录日志。

### 为什么它通过了测试

「文档」就是数据库本身：可枚举（information_schema）、
支持分页，并且已经部分呈现（System 页面的表格大小卡片）。
只读浏览器是指向 `$wpdb` shim 的表面引擎：表格
列表 → 分页行 → 行详情。不需要插件，也不需要新的客户端机制；
构建工作量相较于其作为一个
诊断工具。

### 使其可交付的边界

**只读不是 v1 的妥协，而是产品本身。** 数据库*编辑器*
绕过每个插件的不变量（序列化 Blob、缓存、类似外键的
WordPress 在代码中伪造的约定），并将诊断工具变成一把双刃剑。
写入是永久性的非目标，UI 中明确写出（「从设计上只读」）。

范围草案：

- 系统页面相邻位置（Manage 组、`manage_options`，并考虑设置门控
  秉承与 wp-config 调试工具相同的理念：仅在
  文件修改式的信任机制已经存在）。
- 显示表行数和大小的列表（System 卡片，已提升优先级）、搜索
  按表名限制，默认限定在前缀范围内，并提供显式开关以
  外部前缀表。
- 使用表面引擎的表格渲染器显示分页行；行详情模态框
  复用条目详情的结构。LONGTEXT/blob 列会以截断形式呈现，并带有
  复制控制，序列化值以 RAW 形式呈现，且永远不会反序列化
  （常规 shim 规则甚至保护查看者）。
- 列排序，简单的按列包含过滤。不支持 JOIN，不提供查询框：一个
  SQL 控制台是另一种产品，具有不同的威胁模型，而
  「我需要真正的 SQL」的人：老实说，应使用 WP-CLI 或 Adminer。

### 风险

规模小，主要在于克制：添加「只写一条」写入路径的诱惑
（修正选项中的拼写错误）就是查看者变成编辑者的方式。唯一真正的
技术注意事项：针对超大表执行 SELECT 需要遵守 LIMIT 约束，并且
从 information_schema 估算读取行数上限，否则查看器会变成
在最需要它的确切站点上成为站点杀手。

## 案例研究 3：文件浏览器（开发者界面）

三个案例中最弱的一个，记录它主要是为了划清边界。

- **只读列表 + 文件查看器**（浏览 wp-content，查看日志或
  配置（采用调试日志覆盖层模式）是合理且成本低廉的；
  系统调试工具已经可以按路径读取文件。v0.19.0 的日志查看器
  强化了该案例中「已覆盖」这一半：一个查看器覆盖所有
  该站点拥有的日志（调试日志、单独的 PHP 错误日志、WooCommerce
  渠道，以及通过以下方式获取主机和插件源代码
  `minimal_admin_log_sources` 过滤器位于 `includes/class-minimal-admin-logs.php` 中），
  涵盖实际会出现的诊断读取。不提供通用
  截至 v0.24.0，文件浏览器不存在，也没有排期。
- **文件管理器（写入、上传、chmod、编辑 PHP）不是目标。** 它是
  WordPress 安全中最容易被滥用的界面，它存在于
  面向愿意承担风险的 wp-admin 邻近插件，而除此之外
  Minimal 的产品（平静的日常管理）需要它。
- Disembark 说明：其连接器已经通过以下方式公开了文件/数据库原语
  REST（`disembark/v1/database`、`/stream-file`、`/file/save`，……）并且可能
  原则上可以支持这一点。在 Minimal 将 UI 指向这些路由之前，它们
  需要上游的真实身份验证：截至 v2.7.0，它们注册时不会
  `permission_callback`（令牌检查位于其他位置），而这已经
  标记为上游修复。在 Minimal 自身上限下提供服务器端 shim 访问
  无论如何都应采用该模式（rest_do_request 先例）。
  已交付的 Backups 适配器（v0.12.0，`includes/adapters/disembark.php`）
  严格遵循这一界限：它读取 Disembark 的选项和文件布局
  在 `manage_options` 下执行服务器端处理，并且绝不会调用受令牌保护的
  HTTP 路由；v0.22.0 的恢复新增功能是深层链接，而不是调用。

## 我们永远不会构建的内容（本文档对现有列表的补充）

- 拖放画布的对等克隆（包括表单构建器：80% 编辑器
  这是另一种产品，而画布仍然属于 GF）。
- 数据库写入或 SQL 控制台。
- 文件写入/上传/管理器界面。
- 将其中任何一个置于功能标志后「试试看」：上述边界是
  产品决策，而不是暂存环境。
