# 项目目标

Minimal Admin 的存在是因为 WordPress 管理后台将日常工作埋在二十年的
积累的界面负担。这些原则决定了构建什么以及如何构建。
这些原则服务的可衡量结果——以及用于评判它们的数字——
位于 [roadmap.md](roadmap.md)。

## 目标

1. **让路。** 日常工作——写作、审核、检查站点、管理
   文件和用户——都应一键可达，并在视觉上保持平静。密度服务于读者，而不是
   工具栏。
2. **真正的替代品，而非演示。** Minimal 必须能够在拥有数十万
   行（它是在生产规模的数据集上开发的）。分页、`_fields` 白名单
   和能力门控是不可妥协的要求，而不是优化项。
3. **零锁定。** Minimal 写入的所有内容都是原生 WordPress：Gutenberg 区块标记、核心
   选项和核心 REST 调用。停用插件后，不会丢失或破坏任何内容。Classic
   wp-admin 始终完全可用——Minimal 是增量式的。
4. **无需构建步骤。** 一个原生 JavaScript 文件、一个样式表，以及从上到下读取的 PHP。任何人
   一个下午就能读完整个代码库。框架让人陷入依赖升级的无休止循环，这
   项目有意不纳入。
5. **架构防御。** 列表上下文中绝不运行其他插件的渲染路径（
   行为异常的插件不能拖垮 Minimal），永远不要反序列化外部 blob，
   在服务器端检查能力，在边缘转义所有内容。
6. **生态系统邀请。** 第三方插件通过一个声明式过滤器集成——
   参见 `for-plugin-authors.md`。Minimal 为热门插件提供适配器；插件作者可以提供
   无需编写 JavaScript 即可自行完成。
7. **用户高于所有集成。** 插件注册的任何内容都不得抢占注意力
   用户未要求的内容，以及插件注册的任何内容，都可以由用户隐藏或静音。
   WordPress 在其通知系统中败下阵来；Minimal 通过架构强制执行这一点
   （仅描述符，不托管提取）、预算和每用户控制——绝不与
   相信插件作者会自我克制。参见 `v1-readiness.md`。

## 非目标

- **Gutenberg 对等性。** 复杂的区块布局属于区块编辑器；Minimal 会链接到它
  干净地（`editor-direction.md`）。
- **设置页对等性。** Minimal 呈现人们实际会更改的设置。长尾
  始终停留在 wp-admin 中。
- **暂时不支持多站点网络管理。**
- **成为页面构建器。**

## 质量标准

每项功能交付时都包括：在干净站点上进行浏览器级验证，*以及*生产规模的
站点、零控制台错误、通过 UI 正确隐藏/显示来验证的能力检查，以及一个
Emoji-Log 提交。如果一个功能无法端到端验证，就不算完成。
