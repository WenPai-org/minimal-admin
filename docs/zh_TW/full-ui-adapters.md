# 完整 UI 外掛配接器 — 研究與路線圖

**論點：複雜外掛的完整 UI 支援是一座階梯，而不是懸崖。** 人們擔心
在「完整外掛程式編輯是一項龐大工程」背後的假設，是工作單位為
畫面：永遠手動重建每個外掛的每個管理頁面，且永遠落後。研究
表示工作單位是*結構描述系統*。成熟的外掛已停止手寫
多年前就建立了自己的設定頁面；它們將欄位宣告為資料並渲染
以通用方式。如果 Minimal 能匯入這些宣告，一個轉接器 Mapper 就能涵蓋整個
外掛系列，畫面便會自然產生。

研究依據（2026-07-06）：對 Gravity Forms 2.10.5 與 Gravity 的原始碼層級稽核
SMTP 2.2.0（生態系中兩個最複雜的外掛，刻意選為
針對目前 Minimal 的擴充機制清單（包括棘手案例）。接線
一開始就排除了將其現有管理 UI 搬入 Minimal；問題在於
適配器方式是否能擴展至完整覆蓋範圍。

## 主要發現

1. **兩個外掛在關鍵處都由結構描述驅動。** Gravity Forms 使用一個共用的
   設定引擎（`includes/settings/class-settings.php`，23 種欄位類型），用於其
   外掛設定、表單設定、通知、確認，以及每個附加元件的
   設定與 feeds。Gravity SMTP 將全部 21 個連接器的設定欄位宣告為資料
   （`settings_fields()` 描述器陣列，約 8 種元件類型）。兩者都不會手動撰寫
   設定 HTML。能渲染其結構描述的外部 UI 幾乎可以渲染其所有
   其管理介面，包括尚不存在的附加元件中的畫面。

2. **寫入路徑很乾淨。** GF 的完整表單定義（欄位、設定
   通知、確認）會透過一份 JSON 文件往返傳遞
   `PUT /gf/v2/forms/{id}`；項目、備註與 feeds 具備完整的 REST CRUD。Gravity SMTP
   將所有內容儲存在兩種 JSON 選項格式與四個自訂資料表中，並帶有 nonce'd
   每個變更都有一個 ajax endpoint。不進行畫面擷取，也不使用 POST 至管理頁面的技巧。

3. **Minimal 已經擁有大部分用戶端機制。** 三個由結構描述驅動的表單
   目前存在的系統（編輯器面板、介面建立／編輯、區塊檢查器表單）
   搭配三種不一致的欄位詞彙，以及 `sectionsRoute` 顯示模型
   模式已將詳細資料渲染移至伺服器端。單一最高槓桿
   移動是整合，而非創造。

4. **真正需要客製化的表面很少，而且可以跳過。** 在 GF 中，它是拖放
   表單編輯器（以及小型條件邏輯規則建置器）。在 Gravity SMTP 中，它是
   僅有 Google/Microsoft/Zoho 的 OAuth 交握。兩者的其他部分
   外掛的是清單、詳細資料檢視，以及由結構描述宣告的表單。客製化層級已經
   已有經過驗證的答案：委派，完全如同頁面建置器（「在 Gravity Forms 中編輯」
   只需點擊一次，不需要 wp-admin 外框即可使用建置器風格的畫面）。

## 架構框架：四個階梯

這項提案是一道升級階梯。每個階梯都能獨立交付，且每一階都會
下一級成本更低，且外掛的適配器可以在任何一級停下，使用 wp-admin
深層連結涵蓋其餘內容。整體遵循原則：Minimal 會從結構描述進行呈現
在執行時從現行外掛讀取，因此當外掛新增欄位或附加元件時，
涵蓋範圍會自行更新。手工建置的畫面會過時；匯入的結構描述不會。

### Rung 1 — 一個表單引擎（基石）

將三套欄位詞彙合併為單一由結構描述驅動的表單呈現器，定義為
由 Minimal 提供（而非由任何單一外掛程式提供）：欄位類型包括 text、textarea、number、select，
select-with-custom、radio、checkbox、toggle、hidden，加上每個欄位的 `required`，
`default`、`choices`、`help`、`placeholder`、驗證訊息，以及簡單的
`dependency` 規則（當欄位 A 等於 X 時顯示欄位 B；GF 會評估這些
目前透過一小組運算子在用戶端處理，而 Minimal 的 `when` 條件已經
相同概念）。編輯器面板引擎（`panelInput`/`panelCard`）是目前運作中的
基礎：它已處理選項、切換開關、未儲存變更追蹤，以及鎖定欄位
升級。將它與儲存後 payload 解耦，讓任何呼叫端都能將其指向一個
`{ schemaRoute, valuesRoute, writeRoute }` 三元組。

下游所有功能都會重複使用此機制：表面建立／編輯會為
免費，編輯器面板不會失去任何功能，設定介面也因此成為可能。

### Rung 2 — 設定表面 + 結構描述映射器（乘數效應）

新的表面形狀：

```php
'settings' => [
  'schemaRoute' => 'minimal-admin/v1/gf/settings-schema/{tab}',
  'valuesRoute' => 'minimal-admin/v1/gf/settings/{tab}',
  'writeRoute'  => 'minimal-admin/v1/gf/settings/{tab}',
  'tabs'        => [ ... ],
],
```

用戶端會呈現表單引擎群組的分頁，並將變更後的值以 PUT 傳回。所有
智慧位於轉接器 shim 中，負責兩項工作：

- **結構描述映射。** 將外掛的原生欄位描述器轉換為 Minimal 的表單
  詞彙。這是每個*框架*撰寫一次，而不是每個畫面一次。GF Settings
  映射器（23 種類，其中大多數與 Minimal 一對一映射）涵蓋 GF 外掛設定、表單
  設定、通知、確認，以及每個 GFAddOn 的外掛／表單／feed
  設定，現在與未來皆涵蓋。一個 Gravity SMTP 映射器（約 8 種元件類型）涵蓋所有
  21 個連接器與一般／日誌／警示分頁。無法映射的欄位類型（GF 的
  `generic_map`、`notification_routing`；任何無法解析的 callable）都會
  計算並顯示為「N 個進階欄位 — 在 wp-admin 中編輯 ↗」，正是
  ACF 面板已交付的鎖定欄位模式。
- **值的串接。** 在
  shim，依照外掛自身的 capability 模型。對 GF：`GFAPI`，
  `update_plugin_settings()`，針對通知／確認編輯提供完整表單 PUT，
  一律透過 `GFCommon::current_user_can_any()` 控制。對 Gravity SMTP 而言：
  服務容器的資料儲存區（保留 `GRAVITYSMTP_*` 常數鎖定
  行為），並受細粒度 `gravitysmtp_*` 上限控制。Shim 規則維持不變：
  前綴限定的查詢，絕不包含 `unserialize()` 第三方 blob、敏感欄位
  哨兵值（Gravity SMTP 會將密碼遮罩為 `****************`；未變更的哨兵值
  必須跳過寫入，符合其自身的儲存語意）。

這一階是「完整 UI 支援」不再只是推測的地方：它會將兩者都轉換
外掛的設定範圍，這按畫面數量計佔其管理介面的大部分。

### Rung 4 — 客製化階段（作出決定，不要無意間陷入其中）

對於超出結構描述範圍的介面，有兩項候選政策，而建議是
首先：

- **委派（建議方式，也是目前已發布的模式）。** GF 表單編輯器是
  對 Gravity Forms 而言，就像 Elementor 的畫布之於 Elementor，而 Minimal 已經決定
  遇到這種情況：偵測、深層連結，絕不重建。研究也強化了這點：
  編輯器約有 100 個設定面板是手工撰寫的 inline JS，拖放層則是一個
  完整應用程式，而 GF 自己的編輯鎖定受限於管理畫面（外部編輯器
  會繞過它）。與此同時，收益有限，因為表單*管理*（列表、
  項目、設定、通知）是日常工作；表單的*建置*則是偶發工作。
- **外掛提供的 JS 檢視（已拒絕）。** 允許配接器註冊任意 JS
  檢視將會終結無建置、單檔案、可 grep 架構，以及一個
  安全性回歸（Minimal 文件內含任意第三方程式碼，而該文件
  目前只有刻意設計為頁面層級的 `minimal_admin_template_footer` 逃生口
  允許的範圍（供開發者工具使用）。如果某個畫面無法以描述元表達，
  答案就是深層連結。

長期備註，特此記錄以保留該選項的可見性：GF 的表單編輯器會寫入一個
乾淨且可完整列舉的 JSON 文件（`display_meta`），透過 `PUT /forms/{id}`，
欄位調色盤是以程式產生的（`GF_Fields::get_all()`），每種類型的設定鍵則
可列舉，而條件邏輯只是簡單的規則 JSON。由 Minimal 建置的表單編輯器會
因此*可能*不接觸 GF 的 JS。這將是產品層面的決策，關於
其規模相當於「Minimal 建置第二個編輯器」，不是適配器功能，而層級中沒有任何內容
1-3 會使其無法實現。該選項（「80% 編輯器」），加上開發者表面
兄弟項目，其範圍界線已在 `docs/native-editors.md` 中劃定。
在同系列功能中，唯讀資料庫檢視器已於 v0.22.0 週期發布；
檔案瀏覽功能暫時擱置，而 80% 的編輯器仍是刻意押注，不
尚未完成。

## 風險與待解問題

- **結構描述可呼叫項。** GF 描述器可能攜帶 PHP 可呼叫項（選項、呈現
  回呼）。Mapper 會解析能解析的內容，其餘則計為鎖定欄位；
  絕不嘗試序列化可呼叫物件。
- **完整表單 PUT 並行控制。** 編輯一則通知會往返傳送整個表單
  JSON，因此兩個編輯器可能互相覆寫。透過在
  shim（一次請求、最小視窗），並在此之前檢查 `date_updated`
  寫入；GF 自身的鎖定僅限於管理介面，無法在此提供協助。
- **版本漂移。** 執行時期的結構描述匯入會自動修復欄位，但映射器程式碼
  會接觸外掛內部（GF 的 Settings 類別、Gravity SMTP 的容器名稱）。
  每個 shim 已經檢查外掛是否存在；映射器也必須檢查類別／
  方法存在性，並降級為深層連結，絕不導致致命錯誤。
- **加密 Blob。** GF 外掛程式設定選項在靜態儲存時會加密；一律應
  透過 `get_plugin_settings()`/`update_plugin_settings()`，絕不使用原始選項。
- **範圍紀律。** 此路線圖的失敗模式，是重新打造一次 wp-admin
  一次一個描述元。`stats`/圖表／批次新增功能受限於兩者能提供的內容
  案例研究外掛程式實際需要的內容；只有某個假設中的單一外掛程式會使用的任何內容
  等待該外掛存在。

## 我們永遠不會建置的內容

嵌入外掛管理頁面（iframe 或其他方式）、外掛註冊的 JS 檢視，以及一個
通用的 XML 類版面配置語言、拖放編輯器重建，以及每個畫面手工建立的
外掛程式 UI 的複製品。連結至 wp-admin 並不是道歉，而是逃生
讓每個階梯都保持誠實的逃生口。
