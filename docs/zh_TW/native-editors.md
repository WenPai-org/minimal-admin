# 原生編輯器與開發者介面——介面卡階梯上方的階梯

**狀態：一項已發布，兩項暫緩（更新於 2026-08-06，v0.24.0 中
樹）。**唯讀
資料庫檢視器（案例研究 2）已在 v0.22.0 週期中推出，完全按照
此處劃定的範圍內；Gravity Forms 的 80% 編輯器與檔案瀏覽器維持
暫停且未排程。原始前提仍然成立：此文件存在是為了
當其中一項功能強大到足以投入建置時，範圍論證其實已經
已完成，邊界也已劃定。檢視器證明了該模式
正常運作。它擴充了 `full-ui-adapters.md`，
其四級階梯止於「委派客製化畫面」；這就是地圖
哪些功能可以建立在其上，以及判斷某項功能是否
應該歸屬的位置。

## 決策測試

介面卡階梯的第 4 階表示：當外掛畫面無法以
描述元，直接深連結至該處。此規則混淆了兩種不同情況，而
將它們分開正是整個洞見：

1. **畫面就是畫布。** 互動本身就是產品：拖曳
   Elementor 區段、繪製 Bricks 版面配置、GF 的即時表單預覽。這
   它們產生的成品不是不透明的（建構器中繼資料 blob），就是無法分離
   從呈現迴圈中移出。委派在這裡永遠是正確的。這絕不會
   變更。
2. **畫面是套在整潔文件上的精美表單。** UI 看起來
   複雜，但它*產生*的是可列舉、可往返處理的資料
   具有公開寫入路徑的文件。在這裡，Minimal 不需要該外掛的
   畫面：它可以在 Minimal 的文件中自行建立編輯器，
   慣用方式，而外掛無法分辨其中差異。

因此測試是：**忽略 UI，查看產物。** 它是否是一份整潔的文件
（透過 REST 路由的 JSON、可列舉的結構描述、具版本的選項結構）？
接著原生編輯器便*成為可能*，問題轉為產品範圍。是否
它是不透明的，還是互動才是產品？那麼深層連結就是答案
永久如此，任何需求都不應重新開啟它。

目前有兩個系列通過測試，而且差異足夠大，應分別處理
分開處理：**乾淨文件上的原生編輯器**（Gravity Forms 案例
以及**開發者介面優先於網站原語**（資料庫檢視器、檔案
瀏覽器），其中「文件」本身就是網站。

## 案例研究 1：Gravity Forms 表單編輯器（80% 編輯器）

### 為何通過測試

根據 2026-07-06 的來源研究（詳情見 `full-ui-adapters.md`）：

- GF 表單就是一份 JSON 文件（`display_meta`），可往返傳遞於
  `PUT gf/v2/forms/{id}`。欄位、設定、通知與確認
  全部都存在其中。
- 欄位選擇面板是程式化的：`GF_Fields::get_all()` 會列舉每個
  已註冊的欄位類型，包括附加元件提供的欄位類型。
- 每種類型的設定索引鍵都可列舉，條件邏輯是一套小型規則
  JSON（`{ actionType, logicType, rules: [{ fieldId, operator, value }] }`），
  這是 Minimal 自身的 `when`-條件形狀的成熟版本。
- GF 自己的編輯器是在此文件之上手工撰寫的內嵌 JS。沒有任何
  它所做的事情具有特權；外部編輯器寫入相同文件會產生
  GF 呈現並可互換編輯的表單。

### 範圍決策：80%，而非相容性

一個相容性編輯器（GF 的拖放畫布、約 100 個手工撰寫的設定面板，
即時預覽）未通過畫布測試，並會讓 Minimal 永久處於相容性
跑步機。Stackable 的教訓適用：追逐外掛自己的 React UI 是一條
Minimal 因勝出而輸掉的競賽。

80% 編輯器是不同的產品：**具有欄位編輯功能的表單管理**，
以 Minimal 的清單優先慣用方式，涵蓋人們實際對表單進行的編輯
已經存在的功能：

- **欄位清單**——新增、移除、重新排序（選單拖曳模式）、複製。
  以資料列而非畫布呈現；靜態預覽面板可以渲染表單
  透過 GF 自己的前端標記，在島嶼式預覽中唯讀呈現。
- 透過共用表單引擎提供**每個欄位的基本功能**：標籤、描述，
  必要、預留位置、選項（新增／重新排序／預設值）、欄位大小、管理
  標籤。設定可對應至表單詞彙的欄位類型會獲得完整
  編輯；其餘內容會呈現各自對應的子集，以及帶鎖定的計數，並以
  「在 Gravity Forms 中編輯 ↗」（ACF 鎖定欄位模式）。
- **表單設定、通知、確認**——Phase-2 GF Settings
  對應器 ✅ 已交付（v0.13.0 週期，2026-07-12）：透過
  項目範圍的設定檢視、以清單檢視呈現的通知，以及每日欄位
  編輯；確認編輯已刻意略過（表單建構時
  工作，而非每日工作）。80% 編輯器會與它們組合，而不是
  包含這些內容。
- **條件邏輯，先讀取**：將現有規則呈現為句子
  （「Budget 大於 500 時顯示」）。編輯規則是 v2 的決策；
  規則 JSON 很簡單，但要打造良好的規則 UX 並不簡單。

明確永久排除：拖放畫布、即時樣式化預覽、版面
欄位、定價／產品欄位連接，以及超出該
設定對應器涵蓋的範圍。深層連結只需點擊一次，而 GF 的編輯器很完善。

### 承重風險

- **完整表單 PUT 並行控制。** 一次通知編輯會往返整個
  表單 JSON；兩個編輯器可能互相覆蓋，而 GF 自身的鎖定機制是
  受限於管理畫面，因此無法提供協助。緩解方式：在執行
  寫入前先在 shim 中檢查 `date_updated`，並加上 Minimal 端的鎖定
  如果這項功能曾經推出（`_edit_lock` 模式證明 core 與 Minimal 可以共用
  鎖定協定；GF 需要透過表單中繼資料採用相同概念）。
- **版本漂移。** mapper 在執行階段讀取結構描述，因此*欄位*會自動修復，
  但編輯器對 `display_meta` 結構的假設是程式碼。依
  每次讀取都會降級為深層連結，絕不造成致命錯誤（既定的 shim 規則）。
- **必須明確記錄反覆迭代的界線。** 一旦某個請求需要
  超出表單詞彙的各欄位類型客製化 UI，答案是
  鎖定數量，而不是新的控制項。這正是維持
  讓區塊檢查器保持誠實。

### 成本，坦白說

這是「Minimal 建置第二個編輯器」的規模：可以想像區塊檢查器的工作量，
不是介面卡。欄位清單 + 基本功能 + 測試套件，估計需要完整一個週期。
必要的基礎管線（項目範圍設定、Settings-framework 對應器、
通知寫入路徑）已在 v0.13.0 週期交付，而管理
圍繞暫存編輯器的圈子持續擴大：項目工作流程
（star、spam、bulk、resend）在 v0.12.0，以及 v0.18.0 中的 Feeds 檢視，該檢視
列出每個附加元件來源，並透過 GF 自身的模型提供啟用／停用與刪除
而設定仍維持深層連結，因此「不提供附加元件資料流 UI」
即使來源變得可見，邊界仍然維持。截至 v0.24.0，沒有欄位編輯
程式碼存在於樹狀結構中（`includes/adapters/gravity-forms.php` 僅寫入
透過 `GFAPI::update_form` 進行表單設定與通知）；這些
在做出承諾前仍需完成的事項未變：對該表單管理
在實際使用 Gravity Forms 的網站上進行深度驗證，因此這項押注已獲得回報，
不應視為理所當然。

### 一般化

GF 是參考，而非目標。同樣的 80% 編輯器形態適用於任何外掛
其產物是乾淨文件：Fluent Forms（表單以 JSON 儲存在其自身的
具備 REST 的表格）、Redirection 群組、WP Mail SMTP 連線精靈。
規則：針對最難、但結構良好的案例，一次建立文件編輯器
（GF），將可泛化的部分提取至表單引擎，並讓其他介接器
與對應器一起選擇加入，完全如同設定介面乘數。

## 案例研究 2：資料庫檢視器（開發者介面）

**✅ 已發布（v0.22.0 週期，2026-07-24）** — `/minimal-admin/database`，建置為
以下範圍：`includes/class-minimal-admin-db.php`（三個 GET 路由位於
`manage_options`，針對 information_schema 的識別碼白名單，LIMIT
在 10k 分頁視窗與上限篩選計數的規範下，每個儲存格
位元組上限，並提供較寬裕的資料列詳細資料重新擷取上限），以及專用的用戶端檢視
（資料表清單 → 分頁列 → 列詳細資料 modal）。套件：`tests/database.test.js`。
界線得以維持：沒有寫入、沒有 SQL 主控台，序列化 blob 原樣呈現。

**同一週期內擴充（2026-07-24）**，加入兩項維持
在原始範圍內，並在明確完成採用與否的利弊評估後
再進一步（phpMyAdmin 問題，答案是否定的）：

- **結構分頁**（`GET /db/structure`）— 欄位加上來自 `indexes_of()` 的
  `SHOW INDEX`。僅有中繼資料，因此在任何大小的資料表上都是免費的，這
  為什麼此分頁不受限制，而 Rows 維持視窗化。
- **健康狀態檢視**（`GET /db/health`）——固定的檢查登錄（孤立掃描、
  索引與引擎維護、碎片化、自動遞增容量、修訂版本
  與佇列積壓），快取 10 分鐘，並摘要為一項系統健康
  列。套件：`tests/db-health.test.js`。

三項特性讓這些新增功能不需要新的介面，而任何
未來檢查**必須同時符合三項：**SQL 是由人撰寫的**（沒有請求
參數能夠到達該處，因此不會在其上新增識別碼或注入介面
檢視器已有的功能）；**掃描範圍受限**於相同的 `COUNT_CAP`
子查詢慣用法為 `rows()`，並在 `SCAN_MAX_ROWS` 以上完全略過，因此
診斷工具不會傷害最需要它的大型網站；而且**唯一的
補救方式是提供一個可複製的 WP-CLI 指令**。最後一項是承重核心。
「清理」按鈕正是將此檢視器變成編輯器的關鍵一步，
而以下反對它的理由並未改變。複製指令會把
將寫入交給管理員自己的 shell，在其應在的位置，並維持 Minimal 的主張
確實如此。

在規劃過程中出現、但遭到拒絕的刻意非目標：一個
**資料庫傾印**。唯讀不代表讀取完整資料時就沒有危害。一個
傾印會擴大任何驗證錯誤的影響範圍，從「管理員讀取受限的
一次顯示一頁列」變成「一次請求即可取得每個密碼雜湊、客戶
地址、儲存的 SMTP 密碼與授權金鑰」，以及反覆出現的實際
此領域的 CVE 是某個匯出外掛將 `.sql` 留在可由網路服務的
目錄。Minimal 已經有備份系列（UpdraftPlus、Duplicator、
Disembark、WPvivid），由其負責該威脅模型及復原流程；這
介面或 WP-CLI，才是誠實的答案。如果日後重新檢視，唯一
合理的形態會以串流方式傳送（永不寫入磁碟），由 POST 建立，並
由單次使用的短 TTL 權杖取得，預設僅提供結構，並以
除非明確選擇加入，否則會遮蔽包含認證資訊的欄位，並記錄。

### 為何通過測試

「文件」就是資料庫本身：可列舉（information_schema）、
可分頁，而且已部分呈現（System 頁面的表格大小卡片）。
唯讀瀏覽器是指向 `$wpdb` shim 的介面引擎：表格
清單 → 分頁資料列 → 資料列詳細資料。不需要外掛，也不需要新的用戶端機制；
相較於其作為一項實用功能的價值，建置內容幾乎小得令人尷尬
診斷工具。

### 使其可發布的界線

**唯讀不是 v1 的妥協，而是產品本身。** 資料庫*編輯器*
繞過每個外掛的不變條件（序列化 blob、快取、類似外鍵的
WordPress 在程式碼中偽造的慣例），並將診斷工具變成容易誤用的武器。
寫入是永久的非目標，並在 UI 中明確說明（「唯讀設計」）。

範圍草圖：

- 系統頁面相鄰功能（Manage 群組、`manage_options`，並考慮加上限制
  背後遵循與 wp-config 偵錯工具相同的理念：僅在
  檔案模式的信任機制已經存在）。
- 包含資料列數與大小的資料表清單（提升為 System 卡片）、搜尋
  資料表名稱，預設限定於前綴範圍，並提供明確切換選項以
  外部前綴資料表。
- 使用介面引擎的表格渲染器顯示分頁資料列；資料列詳細資料模態視窗
  重複使用項目詳細資料的形狀。LONGTEXT/blob 欄位會以截斷形式呈現，並附上
  複製控制項，序列化值會以 RAW 呈現，且永遠不會取消序列化
  （即使是檢視器，既有的 shim 規則也能提供保護）。
- 欄位排序、簡單的每欄包含篩選。沒有 JOIN，沒有查詢框：一個
  SQL 主控台是另一種產品，具有不同的威脅模型，而
  對「我需要真正的 SQL」的答案是 WP-CLI 或 Adminer，坦白說。

### 風險

規模很小，主要關乎克制：想要「只加入一條」寫入路徑的誘惑
（修正選項中的錯字）正是檢視器成為編輯器的方式。唯一真正的
技術注意事項：針對大型表格執行 SELECT 時需要遵守 LIMIT 規範，並且
從 information_schema 估算的列數上限，否則檢視器會變成
在最需要它的網站上成為網站殺手。

## 案例研究 3：檔案瀏覽器（開發者介面）

三個案例中最弱的一個，主要是為了劃定其界線而記錄。

- **唯讀清單＋檔案檢視器**（瀏覽 wp-content、檢視日誌或
  設定，以及採用偵錯記錄覆蓋層模式）是合理且成本低廉的；
  系統除錯工具本來就會依路徑讀取檔案。v0.19.0 的日誌檢視器
  強化了此案例「已涵蓋」的部分：一個檢視器即可檢視所有
  網站現有日誌的相同規範（偵錯日誌、獨立的 PHP 錯誤日誌、WooCommerce
  頻道，以及透過以下來源取得主機與外掛程式碼
  `minimal_admin_log_sources` 篩選器（位於 `includes/class-minimal-admin-logs.php`），
  涵蓋實際會遇到的診斷讀取。沒有通用的
  截至 v0.24.0，檔案瀏覽器已存在，且沒有任何排程。
- **檔案管理器（寫入、上傳、chmod、編輯 PHP）不是目標。** 它是
  WordPress 安全性中最常被濫用的介面，它存在於
  願意承擔風險的 wp-admin 鄰近外掛，而這一點
  Minimal 的產品（平靜的日常管理）需要它。
- Disembark 備註：其連接器已透過以下方式公開檔案／資料庫原語
  REST（`disembark/v1/database`、`/stream-file`、`/file/save`、⋯）並可能
  原則上可以支援這些功能。在 Minimal 將 UI 指向那些路由之前，它們
  需要上游的實際驗證：截至 v2.7.0，它們註冊時不會
  `permission_callback`（權杖檢查位於其他地方），而這已經
  已標記為上游修正。依 Minimal 自身上限提供伺服器端 shim 存取
  無論如何都應採用該閘道模式（rest_do_request 先例）。
  已發布的 Backups 介面卡（v0.12.0，`includes/adapters/disembark.php`）
  恰好維持這條界線：它讀取 Disembark 的選項與檔案配置
  在 `manage_options` 下於伺服器端執行，且永遠不會呼叫受權杖保護的
  HTTP 路由；v0.22.0 的還原功能是深層連結，而不是呼叫。

## 我們永遠不會建置的功能（本文件對既有清單的新增項目）

- 拖放畫布的相容性複製品（包括表單建構器：80% 編輯器
  是不同的產品，而畫布仍歸 GF 所有）。
- 資料庫寫入或 SQL 主控台。
- 檔案寫入／上傳／管理介面。
- 將其中任何一項放在功能旗標後「試用」：上述界線
  產品決策，而不是 staging。
